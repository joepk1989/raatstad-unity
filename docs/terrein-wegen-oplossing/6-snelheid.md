# Snelheid: incrementele, lokale herbouw van terrein-met-wegen (Unity/C#)

Budget in the brief: one road edit → rebuild only the affected neighbourhood in ≤ 0.2 s, on ~21,000 hex cells (Goldberg polyhedron, M = 46) in chunks of 128 cells. The existing Raatstad code already has `UseNear` (segments near a cell, remembered per `fieldVer`), `groundCache` keyed by `FieldKey`, `RebuildSome`/`RebuildSteps` (time-sliced), and measures 0.15–0.25 s per click on a full planet (CLAUDE.md). The notes below give the external evidence for the patterns that get such a system under 0.2 s reliably.

---

## KQ1. How do games/engines determine which terrain region a road edit affects, and how do they avoid rebuilding whole chunks?

### Takeaway
The documented pattern everywhere (Catlike Coding hex chunks, Unity Terrain, Minecraft/voxel engines, Cities: Skylines) is the same: an edit marks a *dirty set* (own chunk plus any neighbouring chunk that shares geometry with the edited cell), the dirty set is deduplicated, and the actual rebuild is deferred to one point late in the frame (LateUpdate) so N edits in a frame produce one rebuild per chunk. Engines that model "influence radius" explicitly (Unity Terrain dirty rects, CS1 `TerrainModify.UpdateArea`) pass a rectangle/area rather than a chunk id; chunk-granular systems approximate the area by "cell ± 1 ring of neighbours → their chunks". Detailed CS1/CS2 internals are not publicly documented; only call chains from crash logs are available.

### Cited Findings
**Chunked hex map (direct analogue of Raatstad's `ChunkN` = 128 cells)**
- Catlike Coding Hex Map 5 splits the grid in chunks of 5×5 cells (`chunkSizeX = chunkSizeZ = 5`), explicitly because a single mesh has size limits and because "Editing large maps would become very sluggish otherwise" if every edit retriangulated everything; the author calls chunk size a trade-off (bigger = fewer draw calls, smaller = better frustum culling) with no single right answer — [Catlike Coding, Hex Map 5](https://catlikecoding.com/unity/tutorials/hex-map/part-5/)
- Dirty propagation across chunk borders: `HexCell.Refresh()` refreshes its own chunk *and* every neighbour's chunk when `neighbor.chunk != chunk` (code: `if (neighbor != null && neighbor.chunk != chunk) neighbor.chunk.Refresh();`), because elevation/colour edits change the shared edge/corner geometry between cells — [Catlike Coding, Hex Map 5](https://catlikecoding.com/unity/tutorials/hex-map/part-5/)
- Deferred, deduplicated rebuild: `HexGridChunk.Refresh()` only does `enabled = true`; `LateUpdate()` runs `hexMesh.Triangulate(cells); enabled = false;`. Enabling an already-enabled component has no further effect, so many Refresh calls in one frame collapse into one triangulation per chunk after all edits — [Catlike Coding, Hex Map 5](https://catlikecoding.com/unity/tutorials/hex-map/part-5/)
- Edit classification: in Hex Map 6 a `RefreshSelfOnly()` (`chunk.Refresh();` only) is introduced for edits that "only change the appearance of that cell" (rivers), contrasted with elevation/colour which do affect neighbours; the linked river cell at the other end gets its own `RefreshSelfOnly` — [Catlike Coding, Hex Map 6](https://catlikecoding.com/unity/tutorials/hex-map/part-6/)

**Voxel/chunk engines**
- Veloren (Rust voxel game) MR !119 "rework how chunks get chosen for remeshing": when a chunk is new or changed it queued *all* its neighbours for update, which caused "lots of chunks being remeshed multiple times"; the fix replaced a `LinkedList` with a `HashMap` so each chunk is queued only once. No finer rule (which neighbour actually needs it) and no timings are given — [Veloren MR !119](https://gitlab.com/veloren/veloren/-/merge_requests/119)
- Minecraft's client render sections expose `setDirty`/`scheduleRebuild`, `setNotDirty`, `isDirty`, plus `hasAllNeighbors`/`shouldBuild` (a section waits for neighbours before building) and, in 1.21.9, `isDirtyFromPlayer`/`needsImportantRebuild` (player-caused edits are prioritised) — method names only, from obfuscation mappings; the propagation rules are not described there — [mappings.dev RenderSection 1.21.6](https://mappings.dev/1.21.6/net/minecraft/client/renderer/chunk/SectionRenderDispatcher$RenderSection.html), [1.21.9](https://mappings.dev/1.21.9/net/minecraft/client/renderer/chunk/SectionRenderDispatcher$RenderSection.html)
- A Minecraft renderer add-on (Iodium for VulkanMod) describes the renderer calling `setSectionDirty` on affected sections at every block change, and the add-on tracking dirty sections over a rolling 5-frame window to skip repeat invalidations of sections already queued — [CurseForge Iodium](https://www.curseforge.com/projects/1592048) (single source, not independently verified)

**Unity Terrain (dirty rectangles as the "affected region")**
- `TerrainData.SetHeightsDelayLOD` sets heights without updating LOD/vegetation ("fast enough for live editing"); the manual says to call `TerrainData.SyncHeightmap` once when the edit finishes (e.g. mouse up) to rebuild LOD and vegetation — [Unity docs SetHeightsDelayLOD](https://docs.unity.com/en-us/engine/6000.0/script-reference/unityengine/terraindata/setheightsdelaylod)
- `TerrainData.SetHeights` is slow because it recalculates LOD on every call — [Unity docs SetHeights 2021.1](https://docs.unity3d.com/2021.1/Documentation/ScriptReference/TerrainData.SetHeights.html); [Unity support article](https://support.unity.com/hc/en-us/articles/205486596-Why-is-the-TerrainData-SetHeight-so-slow)
- Older `TerrainData.UpdateDirtyRegion(x, y, width, height, syncImmediately)` had custom paint tools report the modified rectangle so Unity could update collision/physics only there; now obsolete in favour of `DirtyHeightmapRegion`/`CopyActiveRenderTextureToHeightmap` — [Unity docs UpdateDirtyRegion 2019.3](https://docs.unity3d.com/2019.3/Documentation/ScriptReference/TerrainData.UpdateDirtyRegion.html)
- Forum measurement (2019, runtime terraforming): after splitting a 1000×1000 terrain (513² heightmap) into 64×64 chunks (33² heightmaps), syncing 8 changed heightmaps still cost 15–50 ms of GPU stalling; `Graphics.CopyTexture` RT→Texture2D cost 0.1 ms at 1000², 2.3 ms at 5000², 64 ms at 10000²; the main bottleneck was GPU→CPU heightmap sync, and after that "converting the changes into a mesh collider". Suggestions: `DirtyHeightmapRegion(..., TerrainHeightmapSyncControl.None/HeightOnly)`, sync a few heightmaps per frame, sync by camera proximity — [Unity Discussions, SyncHeightmaps performance](https://discussions.unity.com/t/syncheightmaps-and-applydelayedheightmapmodification-performance/738857)

**Cities: Skylines 1 / 2**
- CS1 crash stack traces show the call chain `NetSegment.UpdateSegment → TerrainModify.UpdateArea → TerrainManager.Managers_TerrainUpdated → BuildingManager.TerrainUpdated`, i.e. a road segment update pushes an *area* update to the terrain manager, which then notifies other managers about the terrain update — [Paradox forum thread (stack trace)](https://forum.paradoxplaza.com/forum/threads/cities-skylines-steam-help-error-when-loading-save-creates-some-distorted-glitches-and-wont-let-me-paint-surfaces-nor-landscape.1475724/); [Steam Workshop discussion (stack trace)](https://steamcommunity.com/workshop/filedetails/discussion/689937287/1694922980047130317). The 120×120 m TerrainPatch size and `UpdateArea` semantics from the brief could **not** be confirmed from any public documentation; only the method names are attested.
- CS2 modding guide (community-decompiled) lists a `TerrainSystem` that manages height data and in-game terrain editing, plus `NetTerrainData`, `SurfaceUpdateSystem`, `UpdateAreaResourcesJob` — [ps1ke CS2 guide TerrainSystem](https://ps1ke.github.io/Cities-Skylines-2-Modding-Guide/Game/Simulation/TerrainSystem), [NetTerrainData](https://ps1ke.github.io/Cities-Skylines-2-Modding-Guide/Game/Prefabs/NetTerrainData), [SurfaceUpdateSystem](https://ps1ke.github.io/Cities-Skylines-2-Modding-Guide/Game/Areas/SurfaceUpdateSystem). The page bodies were not retrievable (only navigation index came through), so no field-level details.
- CS2 dev diary "City Corner #4" (performance): on the GPU, LOD models, water simulation and "terrain pathing" generate too many polygons; much generated geometry is culled or discarded for being off-screen or too small — [PCGamesN summary](https://www.pcgamesn.com/cities-skylines-2/performance-blog). CS2 road dev diary describes cut-and-fill construction for roads through terrain — [TechRaptor](https://techraptor.net/gaming/news/cities-skylines-2-dev-diary). Neither gives per-edit terrain update mechanics.
- Transport Fever 2 changelogs only mention "improved terrain alignment" (v1.3) and for the original Transport Fever (2016) "improved performance while building and much better terrain alignment handling" — no mechanism described — [Steam changelog TF2](https://steamcommunity.com/sharedfiles/filedetails/changelog/2718348337?l=danish), [GameWatcher TF patch 12232](https://www.gamewatcher.com/2016-21-12-transport-fever-patch-notes-build-12232)

### Inferences
- For Raatstad the "affected region" of a road edit is derivable analytically, not by chunk heuristics: footprint cells of the edited segment(s) + embankment reach (height difference / `FieldK` slope → horizontal reach; at max 102 m of relief and a 1:1.5 talud that is up to ~150 m, i.e. several cells) + head caps (`EndSlack`, hexagonal kop) + structure footprints (bridge block, mantle, portals, roundabout 7 cells) + **one extra ring of cells**, because a cell's mesh uses its neighbours' corner heights (`CornerH`, `CornerBase0`). Every cell in that set is "dirty"; its chunk is rebuilt (or, better, only that cell's slice of the chunk mesh).
- Catlike's double rule maps 1:1 onto `Rebuild`/`RebuildSome`: collect dirty chunks in a `HashSet<int>` (Veloren's lesson), rebuild once in LateUpdate. If a chunk mesh is a concatenation of per-cell pieces, "rebuilding the chunk" can be a memcpy of unchanged cell pieces plus regeneration of the dirty cells only (see KQ2 caching).
- The graph-wide step is the real risk for the 0.2 s budget: if a road profile/height solve touches the whole graph (e.g. 5000 segments), that has to become local (KQ4), otherwise chunk-local meshing gains are wasted.

### Gaps
- No public documentation of CS1 `TerrainPatch` size (120 m claimed in the brief) or `TerrainModify.UpdateArea` semantics; only crash-trace method names. Decompiling `Assembly-CSharp.dll` would be the only route.
- CS2 modding-guide page bodies (NetTerrainData fields such as flatten/smoothing widths) did not load.
- No GDC talk on Far Cry/Ghost Recon/Horizon terrain editing tools surfaced with the queries used; Townscaper's update strategy is not documented beyond Oskar Stålberg's Twitter (not fetched) — [Unity forum Townscaper thread](https://forum.unity.com/threads/townscaper.964397/) only speculates on the grid deformation.

## KQ2. Caching strategies: content-addressed caches, dependency graphs, spatial indexing of segments

### Takeaway
Content-addressed caching (key = hash of *all* inputs + algorithm version) is a well-established pattern; the practical rule from Houdini PDG is that the cache must be invalidated along the dependency edges, not by inspecting outputs. For "segments within R of a cell" with ~5000 segments, a uniform grid/bucket keyed by cell index is the adequate structure; a BVH is only warranted when segments are long relative to the bucket size.

### Cited Findings
**Content-addressed / memoized caches**
- A memo-key design that pairs *content hash + algorithm name + version fingerprint*, so a hit requires all three to match, guards against stale or cross-version reuse — [coding-agent-search memoization.rs](https://docs.rs/crate/coding-agent-search/latest/source/src/indexer/memoization.rs) (different domain, same key design)
- World-generation pipeline that looks dependent chunks up in a memoized cache before generating them: "Where possible, pull from the memoized cache. Each chunk that doesn't exist is generated and cached." — [blackmagic919, Structure Planning](https://blackmagic919.github.io/AboutMe/2024/06/08/Structure%20Planning)
- Hash functions such as MurmurHash3, xxHash, Wang hash give well-distributed deterministic output from integer inputs; floating-point differences across platforms and thread-completion order can break determinism — [abratabia, Seeds and determinism](https://abratabia.com/procedural-generation/seeds-and-determinism.php)
- Houdini PDG: a work item is reused only if the node has Cache Mode and the expected output file exists; "PDG has no way to generally validate that file is correct – it simply checks if the path exists"; dirty states `DirtyAlways`, `DirtyMissing`, `DirtyNew`, `DirtyStale` (stale = an upstream item wrote new files during the cook); a missing upstream cache invalidates downstream caches; `pdg.WorkItem.invalidateCache()` forces an item *and its dependents* to recook — [SideFX docs workItemCacheState](https://www.sidefx.com/docs/houdini/tops/pdg/workItemCacheState.html), [SideFX forum, Dirty tasks](https://www.sidefx.com/forum/topic/73653), [SideFX forum post 313007](https://www.sidefx.com/forum/post/313007/)

**Spatial indexing of segments**
- A uniform grid is "the simplest spatial data structure"; each cell keeps a list of overlapping objects — [RMIT data-structures notes](https://titan.csit.rmit.edu.au/~e20068/teaching/rtr&3dgp/notes/data-structures.pdf)
- Grid vs BVH (GameDev StackExchange answer): the grid/spatial hash "probably has the theoretical edge in most use cases for construction and updates" provided cells aren't much smaller than typical element size; it "can become very sub-optimal if elements are stored in a large number of cells" (long segments); a BVH can skip whole regions a grid must check cell by cell — [gamedev.stackexchange a/153064 (mirror)](https://backiee.wasmer.app/https_gamedev_stackexchange_com/a/153064)
- A .NET BVH over line segments exists (Euclid.BVH, F#): each segment is in exactly one leaf, "no line has to be split or duplicated"; offers closest-line and lines-near-point queries — [NuGet Euclid.BVH](https://www.nuget.org/packages/Euclid.BVH/)

**Incremental shortest-path (for the dependency/graph side)**
- Ramalingam & Reps (J. Algorithms 1996) give an incremental algorithm for a generalisation of SSSP (Knuth's grammar problem) that handles "an arbitrary mixture of edge insertions, edge deletions, and edge-length changes" between updates; SSSP with positive edge lengths is a special case — [UW-Madison abstract](https://research.cs.wisc.edu/wpis/abstracts/jalg96.abs.html); [IBM Research entry](https://research.ibm.com/publications/an-incremental-algorithm-for-a-generalization-of-the-shortest-path-problem)
- Later benchmarking judged Ramalingam–Reps "usually better in practice on running time, despite a worse worst-case bound" — [optimization-online 732.pdf](https://optimization-online.org/wp-content/uploads/2003/09/732.pdf)

### Inferences
- For Raatstad's existing `groundCache` keyed by `FieldKey`: make the key a hash of *everything* the cell's ground depends on — cell terrain heights of the cell and its 6 neighbours (and ring 2 if `RoadCorner`/`SkewPathCorner` reach there), the set of nearby segment ids with their level, style, width, `OneWay`/`Bike`, bore state, cuts (`CutsNear`), scorch, plus a `PlanetCity.GroundVersion` constant bumped whenever the generation code changes (the PDG/memo-key lesson: algorithm version is part of the key). Then a cache hit is safe without any dirty bookkeeping, and the dirty set is just "cells whose key changed".
- Dependency direction (PDG lesson): invalidate forward along dependencies — segment changed → cells within reach R of the segment → their chunk meshes → their colliders. Never try to detect staleness from the output.
- Spatial index: at hex spacing ~ Planet radius 600 m → cell pitch ≈ 23–25 m (10·46²+2 = 21,162 cells on a sphere of 4π·600² ≈ 4.52 M m² → ≈ 214 m² per cell → pitch ≈ 15.7 m across flats; recompute from `Planet` in code). Segments are cell-to-cell (one pitch long), so "cell index → list of segment ids touching this cell or its 1–2 rings" is a perfect bucket structure: segment length ≈ bucket size, no duplication problem, O(1) update when a segment is added/removed. For a 40 m query radius, ~2–3 rings ≈ 19–37 buckets. A BVH is unnecessary at 5000 segments (the GameDev SE argument: grids win when elements are not long relative to buckets and updates dominate).
- Cheap first check before any mesh work: compare the new per-cell key with the cached key; only cells with a changed key go in the dirty set. This bounds the work to the true influence region even if the first "affected region" estimate is generous.

### Gaps
- No published head-to-head C# benchmark of uniform grid vs BVH for a few thousand segments; recommendation is by argument, not measurement.
- Ramalingam–Reps abstract does not state the "bounded incremental" cost claim (cost proportional to the size of the change); that is in the full paper, which was not fetched.

## KQ3. Unity specifics for fast mesh rebuild (MeshDataArray, Jobs/Burst, GC, MeshCollider bake, time-slicing, measured costs)

### Takeaway
Unity's own numbers: the 2020.1 MeshData API + Jobs + Burst builds a 4.6 M-vertex combined mesh in 60–70 ms versus 760–920 ms (and 640 MB of GC garbage) with the classic main-thread API — a 12× speed-up and ~2000× less garbage. Scaled linearly, a 50 k-triangle rebuild is on the order of 1–2 ms of CPU with the fast path. MeshCollider baking is the hidden cost (155 ms spikes reported); `Physics.BakeMesh` is thread-safe and meant to run in an `IJobParallelFor` before `sharedMesh` is assigned.

### Cited Findings
**Mesh API performance (Unity-reported)**
- Unity 2020.1 Mesh API design doc: combining a 4.6 M-vertex scene took 0.75 s with the regular main-thread API and 0.08 s with Jobs + Burst + the new API — [Unity design doc (Google Docs PDF)](https://docs.google.com/document/d/1QC7NV7JQcvibeelORJvsaTReTyszllOlxdfEsaVL2oA/export?format=pdf) (as quoted in search; the PDF itself returned HTTP 400 on fetch)
- Unity MeshApiExamples readme: "Combine many input meshes into one" (11,466 objects, 4.6 M vertices): regular API 760 ms with 23 k GC allocations totalling 640 MB (2018 MacBook Pro i9) / 920 ms (Threadripper 1950X); Jobs + Burst with MeshData: 60 ms with 0.3 MB GC / 70 ms. "Procedural water" (400×400 grid, full frame times incl. rendering): single-threaded C# 155 ms, single-threaded Burst 38 ms, multi-threaded Burst 9 ms, GPU compute 4 ms (MacBook Pro); 208 / 45 / 11 / 2 ms (Threadripper + GTX 1080 Ti) — [Unity-Technologies/MeshApiExamples readme](https://github.com/Unity-Technologies/MeshApiExamples/blob/master/readme.md)
- `Mesh.AllocateWritableMeshData`: "You can access the resulting MeshDataArray and MeshData structs from any thread"; "Creating a MeshDataArray has some overhead for memory tracking and safety reasons, so it is more efficient to make a single call ... and request multiple MeshData structs in the same MeshDataArray than it is to make multiple calls." Workflow: `SetVertexBufferParams` → write `GetVertexData<T>()`, `SetIndexBufferParams` → write `GetIndexData<T>()`, `subMeshCount` + `SetSubMesh`, then `Mesh.ApplyAndDisposeWritableMeshData` on the main thread — [Unity docs AllocateWritableMeshData 6000.0](https://docs.unity.com/en-us/engine/6000.0/script-reference/unityengine/mesh/allocatewritablemeshdata)
- `MeshDataArray` is for C# Job System access; `AcquireReadOnlyMeshData` for reading many meshes, `AllocateWritableMeshData` + `ApplyAndDisposeWritableMeshData` for creating — [Unity docs Mesh.MeshDataArray 2020.1](https://docs.unity.cn/cn/2020.1/ScriptReference/Mesh.MeshDataArray.html)
- `MeshUpdateFlags`: `DontValidateIndices` (skip index range checks in `SetIndexBufferData`), `DontRecalculateBounds` (skip bounds recomputation in `SetSubMesh`), `DontNotifyMeshUsers` (don't notify Renderers of a possible bounds change), `DontResetBoneBounds`, `DontValidateLodRanges`; "you must ensure that the data you are supplying is valid". No quantified gains given — [Unity docs MeshUpdateFlags](https://docs.unity.com/en-us/engine/current/script-reference/unityengine/rendering/meshupdateflags)
- `Mesh.SetVertices(NativeArray<T>, start, length, flags)` uploads a sub-range; the Mesh keeps no reference to the source container (reuse/dispose after the call); `DontRecalculateBounds` "can prevent the automatic (and potentially costly) recalculation of the mesh bounds"; `Mesh.MarkDynamic` "may improve performance by optimizing the underlying GPU buffer strategy" for frequently updated meshes — [Unity docs Mesh.SetVertices 6000.6](https://docs.unity.com/en-us/engine/6000.6/script-reference/unityengine/mesh/setvertices)
- Forum anecdote: a developer with ~50,000-vertex meshes found `mesh.SetVertices` to be "the main problem in their frame rate drop" (no ms given; context: per-frame updates) — [Unity Discussions, Dynamic Mesh Performance](https://discussions.unity.com/t/dynamic-mesh-performance/581532); another team found it too slow for a per-frame trail renderer and moved to compute buffers — [Unity Discussions, GetNativeVertexBufferPtr](https://discussions.unity.com/t/mesh-vertices-manipulation-performance-understanding-mesh-getnativevertexbufferptr/663822)

**MeshCollider baking**
- `Physics.BakeMesh`: baking = creating "spatial search acceleration structures"; normally happens when a `MeshCollider` is instantiated or `sharedMesh` is assigned; "resource-intensive", so bake ahead or spread across cores; the mesh instance stores the result; reuse only if `cookingOptions` match exactly, the transform allows sharing (no negative/skewed scale), and the geometry hasn't changed; "BakeMesh is thread-safe and computes on the thread it's called from"; don't bake the same mesh from two threads; in a Player the mesh needs Read/Write enabled. Official example: `IJobParallelFor` calling `Physics.BakeMesh(meshIds[index], false)` with `NativeArray<EntityId>` (Unity 6: `mesh.GetEntityId()`; the `int instanceID` overloads are obsolete), then assign `sharedMesh` on the main thread. Note: adding a `MeshCollider` to a GameObject that already has a `MeshFilter` sets `sharedMesh` automatically and can trigger a re-bake — [Unity docs Physics.BakeMesh](https://docs.unity.com/en-us/engine/current/script-reference/unityengine/physics/bakemesh)
- Measured spike: `Physics.BakePhysXCollisionMeshData` 155 ms on the main thread when adding a MeshCollider to an imported mesh (Unity 6.0 beta, vertex count not given); recommended fix: "run the bake in a job before activating the object" — [Unity Discussions](https://discussions.unity.com/t/physics-bakephysxcollisionmeshdata-taking-160ms-on-main-thread/1515199)
- Historical scale (2017 beta regression, since fixed): adding a MeshCollider went from 17 ms → 159 ms, and for a larger mesh 62 ms → 840 ms — [Unity Discussions, b10 vs b9](https://discussions.unity.com/t/adding-a-meshcollider-much-slower-in-b10-than-in-b9/683604) (the issue-tracker page is gone — [404](https://issuetracker.unity.com/api/v1.0/redirects/slug/regression-generating-a-meshcollider-took-5-10-times-longer)). Useful only as an order of magnitude: tens of ms per medium mesh.
- "Mesh.Bake Scaled Mesh PhysX CollisionData" halts when spawning 50 vehicles with MeshColliders — [Unity Discussions](https://discussions.unity.com/t/switched-from-boxcollider-to-meshcollider-now-game-halts-when-spawning-objects/670591)
- `Physics.BakeMesh` is the only exposed way to bake for PhysX; with Unity Physics (DOTS) colliders can be created inside jobs — [Unity forum, async mesh collider cooking](https://forum.unity.com/threads/async-mesh-collider-cooking.950479/)

### Inferences
- Budget arithmetic for Raatstad (inference from the Unity numbers): a chunk of 128 cells at, say, 400 triangles/cell ≈ 50 k triangles ≈ 75–150 k vertices. Linear scaling of 60–70 ms per 4.6 M vertices gives ≈ 1–2 ms per chunk for a Burst/MeshData build+apply. Even the classic path (760 ms / 4.6 M) is ≈ 12–25 ms per chunk, but with ~10 MB of GC garbage per chunk — that garbage is the likely source of the current 0.15–0.25 s per click (GC spikes), more than the vertex math itself. First measure with the Profiler: `GC.Alloc` on `BuildChunk`/`BuildCell`.
- Order of cheap wins, no job system required: (1) reuse `List<Vector3>`/`List<int>` buffers (`Clear()`, never `new`) and `mesh.SetVertices(list)`/`SetTriangles(list, submesh, calculateBounds: false)`; (2) `MeshUpdateFlags.DontValidateIndices | DontRecalculateBounds | DontNotifyMeshUsers` on `SetIndexBufferData`/`SetSubMesh`, set `mesh.bounds` yourself from the chunk's known cell positions; (3) keep the `Mesh` object and overwrite it (`mesh.Clear(keepVertexLayout: true)`) instead of `new Mesh()` per rebuild; (4) `MarkDynamic` is for per-frame updates, not needed for edit-time rebuilds.
- Next tier: build cell pieces into `NativeArray`s in an `IJobParallelFor` (one job index per dirty cell) writing into a single `MeshDataArray` allocated with one `AllocateWritableMeshData(dirtyChunkCount)` call (the docs' "one call, many MeshData" advice), then `ApplyAndDisposeWritableMeshData` on the main thread. Requires the per-cell geometry code (`PlanetCity.Shapes`, `RoadDraw`) to be Burst-compatible (no managed objects) — a large refactor; do it only if the simple path misses the budget.
- Colliders: the clear hazard. Assigning `MeshCollider.sharedMesh` on a 50 k-triangle chunk likely costs tens of ms on the main thread (155 ms reported for one imported mesh). Pattern: after the chunk mesh is applied, schedule `Physics.BakeMesh(mesh.GetEntityId(), false, cookingOptions)` in a job, complete it next frame (or let it run while the frame renders), then assign `sharedMesh` with identical `cookingOptions`; or defer collider updates by one frame and only for chunks near the camera/walker (the SyncHeightmaps thread's "sync by proximity" advice). Picking uses the collider; if picking tolerates a one-frame-old collider the user won't notice.
- Time-slicing (`RebuildSteps` already exists): Catlike's LateUpdate pattern plus a per-frame budget (e.g. 8 ms) — rebuild the chunk under the mouse first (as `RebuildSome` does), the rest in order of distance to the camera. With `AllocateWritableMeshData` the heavy part runs on worker threads during the frame anyway.

### Gaps
- No published measurement of `Mesh.SetVertices`/`SetTriangles` in ms for a given vertex count on current Unity; all claims above are scaled from Unity's 4.6 M-vertex combine benchmark (combine ≠ generate, but both are dominated by vertex copies and apply).
- No published ms-per-triangle figure for `Physics.BakeMesh`; the 155 ms report lacks a triangle count. Must be measured in the project (Profiler marker `Physics.BakePhysXCollisionMeshData`).
- Whether `ApplyAndDisposeWritableMeshData` itself has a significant main-thread cost for ~150 k vertices is not documented; the combine benchmark (60 ms total for 4.6 M incl. apply) suggests it is small.

## KQ4. Determinism and incremental graph solves: can a slope-constrained road height profile be re-solved locally with far nodes fixed?

### Takeaway
Yes, when the profile is the McShane–Whitney-type Lipschitz extension (inf over anchors of `h(a) + g·d(a,x)`, computed as a shortest-path relaxation): the formula is defined pointwise through distances, so a node's value depends only on anchors within the radius where `g·d` could still beat the current value; the extension agrees with the given values on the anchor set; adding constraints can only lower the inf (tighten). Re-solving a bounded subgraph with boundary nodes held at their current (globally valid) values yields exactly the same result as a global re-solve, provided the boundary lies outside the region where the edit changes any value. Neighbour agreement in meshes then follows from determinism: same inputs → same cached piece.

### Cited Findings
- McShane–Whitney extension: for a Lipschitz `f : U → R` on a subset of a metric space "there always exist Lipschitz continuous maps M → R that extend f and have the same Lipschitz constant as f", explicitly `f̃(x) := inf_{u∈U} { f(u) + k·d(x,u) }` with `k` a Lipschitz constant of `f` on `U`; pointwise infimum/supremum of a family of Lipschitz functions with a common constant is Lipschitz — [Wikipedia, Lipschitz continuity](https://en.wikipedia.org/wiki/Lipschitz_continuity)
- `F(x) = inf_{a∈A} [f(a) + d(a,x)]` is a 1-Lipschitz extension of `f`, "first proved by McShane and independently by Whitney" — [arXiv 1907.09214v2](https://web3.arxiv.org/pdf/1907.09214v2); a constrained Lipschitz extension problem "recovers the well-known extensions due to McShane and Whitney" as its most particular case — [arXiv 2310.13554](https://arxiv.org/pdf/2310.13554v3); graphs are metrised "by equipping them with the shortest-path distance" in Lipschitz-extension work — [arXiv 2603.03549](https://arxiv.org/html/2603.03549v1)
- Incremental SSSP under edge insertions/deletions/length changes is a solved problem (Ramalingam & Reps 1996), with SSSP on positive lengths as a special case — [UW-Madison abstract](https://research.cs.wisc.edu/wpis/abstracts/jalg96.abs.html); it is judged "usually better in practice" than competitors despite a worse worst-case bound — [optimization-online 732.pdf](https://optimization-online.org/wp-content/uploads/2003/09/732.pdf); Demetrescu's variant does better when few affected nodes have alternative shortest paths — [KIT publication](https://publikationen.bibliothek.kit.edu/1000052742/3801174)
- Deterministic generation prerequisites: hash functions (xxHash, Murmur3, Wang) give deterministic results from integer inputs; floating-point platform differences and thread completion order break determinism — [abratabia, Seeds and determinism](https://abratabia.com/procedural-generation/seeds-and-determinism.php)
- Neighbour agreement at chunk borders is achieved in the hex-map tutorial not by double buffering but by refreshing every chunk that shares the edited cell's geometry in the same LateUpdate — [Catlike Coding Hex Map 5](https://catlikecoding.com/unity/tutorials/hex-map/part-5/)

### Inferences
- **Why local re-solve is exact (argument, not a cited theorem for the discrete case).** Model: anchors `A` (nodes with a prescribed height: cells the player levelled, fixed-level roads, bridge/tunnel portals), constraint `|h_i − h_j| ≤ g·d_ij` on every link, and the profile taken as the upper McShane extension `h(x) = min_{a∈A} (h_a + g·D(a,x))` (or the lower one with max/−g; or the average). `D` is shortest-path distance along the road graph — exactly a Dijkstra relaxation with edge weights `g·d_ij` from multiple sources initialised at `h_a`. Properties: (i) `h` agrees with the anchors on `A` (McShane). (ii) Monotonicity: adding an anchor or shortening a path can only *lower* the min (tighten); removing one can only raise it. (iii) Locality: an edit at node `e` can change `h(x)` only if a shortest-path-from-anchor route through the edited region beats the current `h(x)`, i.e. only for `x` with `g·D(e,x) < h(x) − h_min_reachable`; since `h` is bounded by the terrain range (−12…90 m, 102 m span) the influence radius is at most `102 m / g` along the graph (e.g. g = 0.15 → 680 m; g = 0.06 → 1.7 km), and in practice far less because a competing anchor nearby wins first. (iv) Domain decomposition: take the subgraph `S` = nodes within radius `K` links of the edit such that the current `h` on the boundary `∂S` is provably unchanged (check: for every boundary node, `h_old(b) ≤ h_new candidates through S`); fix `∂S` as extra anchors and run Dijkstra inside `S`. Because the global solution restricted to `S` with boundary values fixed is itself the McShane extension on `S` (the inf over outside anchors is already encoded in the boundary values on every path leaving `S`), the local solve returns the global values. If a boundary value *would* change, grow `K` and repeat — this is the standard affected-set expansion of Ramalingam–Reps, which handles exactly these mixed insert/delete/relength updates.
- **Caveat on deletions:** removing an anchor or a link can *raise* values (loosen); the affected set is the set of nodes whose current shortest anchor-path used the removed element. Ramalingam–Reps tracks this via "affected vertices"; a simple safe fallback for Raatstad is to re-solve the connected component containing the edit (components on a sphere planet are typically small villages or one big network — the big network is the costly case, so do the bounded version there).
- **Determinism requirements so cached cell pieces agree with neighbours:** (a) the profile solve must be deterministic — Dijkstra with a priority queue is deterministic if ties are broken by node id, and `float` sums are deterministic on one machine/thread; avoid parallel reductions whose summation order varies (the "thread completion order" pitfall). (b) Each cell's mesh must read only inputs that are in its cache key; shared corner heights (`CornerH`) computed from the three cells around the corner are the same function in all three cells → identical vertices → no cracks. (c) Rebuild in "rings": dirty set = influence region + 1 ring, all rebuilt in the same LateUpdate, so no frame shows a seam — this is Catlike's approach and makes double-buffering unnecessary. Double-buffer (`mesh A` shown while `mesh B` is filled) only matters if the rebuild spans several frames; with `AllocateWritableMeshData` the new data is applied atomically per mesh, so the old chunk stays visible until `ApplyAndDisposeWritableMeshData` — effectively free double buffering.

### Gaps
- No source was found that states the discrete, graph-metric McShane extension's locality/domain-decomposition property explicitly; the argument above is derived from the pointwise inf formula (cited) and standard shortest-path reasoning. The "bounded incremental" cost statement of Ramalingam–Reps is in the full paper, not in the fetched abstract.
- No published example of a city builder documenting a local re-solve of road grades; CS2's `NetTerrainData`/terrain-system details were unreachable.

## Summary checklist for Raatstad (inference, ordered by expected gain per effort)
1. Profile with the Unity Profiler on a full planet click: split `GC.Alloc` vs `BuildChunk` CPU vs `MeshCollider.sharedMesh` (`Physics.BakePhysXCollisionMeshData`) vs any graph-wide pass. Published numbers say the collider bake and GC garbage are the usual culprits, not vertex math.

6. Graph solve: local Dijkstra inside a K-ring subgraph with boundary clamped; expand K if a boundary value would change; deterministic tie-breaking.
