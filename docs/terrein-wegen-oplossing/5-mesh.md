Scope note: this covers (1) CDT/TIN with breaklines, (2) walls/jumps, (3) exact agreement on shared patch edges, (4) robust polygon splitting, (5) flat-shaded rendering of ground + wall quads, plus the civil-engineering "corridor/daylight" model. Sources are mostly primary docs (Autodesk help, Shewchuk, Clipper2, Catlike Coding, Columbia/Jacobson project page, Khronos/GameDev threads). ## Q1. Triangulating a height function with crease lines (breaklines): CDT, TIN-with-breaklines, libraries

### Takeaway
A piecewise-linear surface with creases is exactly what GIS/CAD call a TIN with breaklines, built with a constrained Delaunay triangulation (CDT): every crease segment is forced to be a triangle edge, and no triangle may cross it. The standard reference algorithm/implementation is Shewchuk's Triangle (2D only, PSLG input, exact predicates); for C#/Unity the usable ports are Triangle.NET (true CDT, licence caveat), LibTessDotNet (robust tessellator, handles coincident vertices, but no Delaunay/constraint guarantee), poly2tri (CDT, reported less robust). Civil 3D/ArcGIS both describe breaklines as "force triangulation along the line, prevent triangulation across it".

### Cited Findings
- Definition: a CDT takes a planar straight-line graph (points + non-crossing segments), "includes all input segments as edges, and uses only the input vertices"; it generalizes the empty-circle property: each edge has a circle through its endpoints containing only vertices that are *blocked* from an endpoint by an input segment; "A triangulation satisfying these properties always exists" (Chew 1989, Algorithmica 4(1):97–108, doi 10.1007/BF01553881). Several algorithms run in O(n log n); the CDT of a simple polygon can be built in linear time (Chin & Wang 1999). — [Wikipedia: Constrained Delaunay triangulation](https://en.wikipedia.org/wiki/Constrained_Delaunay_triangulation)
- Shewchuk & Brown define: a triangulation T of PSLG X is a CDT iff "every edge in T that is not a segment in X is locally Delaunay"; Chew's divide-and-conquer algorithm has been implemented, Seidel's apparently not. (snippet) — [Shewchuk & Brown, incremental segment insertion in CDTs](https://people.eecs.berkeley.edu/~jrs/papers/inccdtj.pdf)
- Triangle is a "Two-Dimensional Quality Mesh Generator and Delaunay Triangulator"; it produces "exact Delaunay, constrained Delaunay, and conforming Delaunay triangulations"; the -D switch selects Ruppert's algorithm (all triangles truly Delaunay, segments get split); its robust geometric predicates are public domain, Triangle itself is copyrighted and "may not be sold or included in commercial products without a license". — [Triangle home page](https://www.cs.cmu.edu/~quake/triangle.html)
- Terminology: in Triangle, a PSLG's segments are "edges whose endpoints are vertices in the PSLG, and whose presence in any mesh generated from the PSLG is enforced"; "constrained" keeps segments unsplit, "conforming" (-D) may split them. — [RTriangle reference manual (R port of Triangle)](https://packages.oit.ncsu.edu/cran/web/packages/RTriangle/refman/RTriangle.html)
- Shewchuk's predicates: `orient2d/orient3d/incircle/insphere`, "adaptive precision, robust versions" and "fast" non-robust ones; work on IEEE-754 radix-2 exact-rounding hardware; "only the sign, and not the magnitude, of the determinant is needed"; sensitive to extended-precision FPU registers (fix with `volatile`); public domain. — [Shewchuk, Robust Adaptive Floating-Point Geometric Predicates (abstract)](https://people.eecs.berkeley.edu/~jrs/papers/robust-predicates.abstract); [predicates.c copy on CTAN](https://ftp.riken.jp/CTAN/graphics/asymptote/predicates.cc)
- ArcGIS TIN: "Constrained Delaunay" adds each breakline segment as a single edge; Delaunay is honored everywhere except along breaklines, which are not densified; the default "Delaunay conforming" may densify breaklines into several triangle edges. "Hard" breakline = "a border with a sharp discontinuity in elevation, such as the edge of a cliff, a wall, or a curb"; "soft" = smooth elevation change. Delaunay cannot be guaranteed with angular (geographic) coordinates; use a projected system. — [ArcGIS Pro: Edit TIN](https://pro.arcgis.com/en/pro-app/3.5/tool-reference/3d-analyst/edit-tin.htm); [ArcGIS Pro: Create TIN](https://pro.arcgis.com/en/pro-app/3.5/tool-reference/3d-analyst/create-tin.htm)
- Civil 3D: "Breaklines force surface triangulation along the breakline preventing triangulation across the breakline." Typical uses: retaining walls, kerbs, ridge tops, streams. Types: Standard (from 3D lines/feature lines/3D polylines/splines), Proximity (XYZ of vertices taken from nearest existing triangulation points), Wall ("stored as a standard breakline, but defined differently": one offset side for the whole line + a level difference per vertex or for all), Non-destructive ("maintains the integrity of the original surface"), import from FLT files; "Allow Crossing Breaklines" option exists; curved polylines are tessellated by a mid-ordinate distance. — [Civil 3D 2024: About Breaklines](https://help.autodesk.com/cloudhelp/2024/ENG/Civil3D-UserGuide/files/GUID-FCCAF28A-506B-4773-9706-DD1F1F8CC933.htm)
- Civil 3D breakline text-file type letters: P, S, W, L, R, N/ND = Proximity, Standard, Wall, Wall Left, Wall Right, Non-destructive. (snippet) — [Civil 3D: To Create Breakline Data in a Text File](https://help.autodesk.com/cloudhelp/2015/ENU/Civil3D-UserGuide/files/GUID-8DA2A6E0-4505-4BC7-8940-22E8790688E3.htm)
- LandXML 1.1 `Breakline` element: "defined by a 2D north/east or 3D north/east/elev list of points", attributes `brkType` (type `breakLineType`), `desc`, `name`, `state`. The enumeration values of `brkType` were not visible in the result (third-party schema mirror; check the official XSD). — [LandXML Breakline element (schema mirror)](https://schemas.liquid-technologies.com/NIEM/2.0/breakline.html); [Civil 3D: supported LandXML data](https://help.autodesk.com/cloudhelp/2022/ENU/Civil3D-UserGuide/files/GUID-4D10ABA5-5EA0-41A8-BB61-C3F446CE7C6B.htm)
- Feature lines added as breaklines can have no effect if they lack elevation data, or if "Non-destructive breakline" is ticked; fix = remove/re-add via Add Breaklines. — [IMAGINiT: Feature Lines Not Acting as Breaklines](https://resources.imaginit.com/support-blog/civil-3d-feature-lines-not-acting-as-breaklines)
- Libraries (C#): Triangle.NET "generates 2D constrained Delaunay triangulations and quality meshes", based on Shewchuk's Triangle; README warns against commercial use because of Triangle's licence. LibTessDotNet: "robust, fast tessellator", handles self-intersecting polygons and coincident vertices, single or double precision, "handles polygons computed with Clipper". A Unity forum user reports poly2tri "not robust in some cases" and LibTessDotNet failing at times "unless doubles were used instead of floats". — [Triangle.NET (wo80)](https://github.com/wo80/Triangle.NET); [eppz fork of Triangle.NET](https://github.com/eppz/Triangle.NET); [LibTessDotNet](https://github.com/Syomus/LibTessDotNet); [Unity discussions: computational geometry library](https://discussions.unity.com/t/looking-for-a-computational-geometry-library/727568)

### Inferences
- For a *single hex cell or chunk polygon* whose surface is min/max of a handful of planes, a general CDT is overkill: the crease lines are known analytically (plane–plane intersections), so splitting the cell polygon along those lines (Q4) yields convex planar pieces that can be fan-triangulated with no Delaunay step at all. CDT becomes necessary only when breaklines cross each other arbitrarily inside one face (then "Allow Crossing Breaklines" semantics: insert the crossing point as a vertex on both).
- LibTessDotNet is a tessellator (polygon → triangles, winding rules), not a CDT: it does not guarantee that an interior crease segment stays an edge unless the crease is a polygon boundary. To use it for breaklines, split the face polygon along the crease first, then tessellate the pieces.
- "Hard breakline" (ArcGIS) = the crease where two planes meet (talud foot, talud top, road edge); "soft" has no counterpart in a piecewise-planar model.

## Q2. Representing jumps (walls/cliffs): double breaklines vs explicit vertical quads; how CAD TINs and games do it

### Takeaway
A TIN is a 2.5D function and cannot contain a vertical face; Civil 3D's "wall breakline" fakes it by generating a second line parallel to the first with an imperceptible horizontal offset and triangulating between them (practitioners use ~0.01 ft / 0.001 m), and corridor surfaces need an "overhang correction" (follow top links or bottom links) precisely because curbs/walls make the assembly vertical or overhanging. Heightmap game terrains (Unity Terrain, Godot HeightMapShape3D) cannot do overhangs or vertical cliffs either; mesh-based hex terrains (Catlike Coding) draw a cliff as an explicit quad between the lower and upper cell edges, with exactly shared vertices. In Civil 3D/Cities Skylines 2, retaining walls are separate assets/meshes placed against the cut.

### Cited Findings
- Civil 3D wall breakline: the base line is "extended by creating new polyline segments and vertices parallel to the original polyline"; you "select a polyline, or line, and select the offset side"; per vertex you set the vertex elevation and offset vertex elevation or only the "offset elevation difference"; or one difference "to be applied for all offset vertices". — [Civil 3D 2015: About Creating Wall Breaklines](https://help.autodesk.com/cloudhelp/2015/ENU/Civil3D-UserGuide/files/GUID-67133CC6-D9DD-45B3-90F9-DA9FD0F2A3A7.htm); [To Create Wall Breaklines](https://help.autodesk.com/cloudhelp/2015/ENU/Civil3D-UserGuide/files/GUID-D9F76227-73D0-4467-9613-D9DEB4C8A3A3.htm); API: [WallBreaklineCreationData](https://civapidocs.com/2026/e43948cf-88ce-f171-b932-7bbd8f8bb112.htm), [IsRightSideOffset](https://help.autodesk.com/cloudhelp/2022/ENU/Civil3D-API/files/html/44ab184f-6b2c-f55f-dc62-28a8b1c1b5d2.htm)
- Forum explanation (snippet; page 403 to fetcher): Civil 3D "internally generates another line, parallel to the break line with an imperceptible offset, according to the 'side' chosen, and then triangulates from both lines' points"; the side is "the side for the new offset line that represents the elevation of material on the other side of the wall". — [Autodesk forum: The concept of wall break line](https://forums.autodesk.com/t5/civil-3d-forum/the-concept-of-wall-break-line/m-p/11293156)
- Practitioner advice (snippets): "TIN can't have perfectly vertical faces, so a small horizontal offset is required"; typical offset "0.01 ft or so" / about 0.001 m; add elevation points along the wall so the face has enough vertices. Alternative: grading criteria with cut/fill slopes 0.001:1 applied to a feature line; the offset-and-breakline method "commonly gives an error or broken surface". — [r/civil3d: create a wall on my surface](https://lr.in.psf.lt/r/civil3d/comments/1jq8odr/how_can_i_create_a_wall_on_my_surface); [Arkance: How to create Retaining Wall using Grading](https://emea.support.arkance.world/hc/lt/articles/36468675238034-How-to-create-Retaining-Wall-using-Grading); [AUGI: Fine Tuning Civil 3D Contours](https://forums.augi.com/archive/index.php/t-79230.html)
- Corridor overhang: "When subassemblies are joined to form an assembly, surfaces of the subassemblies can overhang one another"; fix via Surfaces tab → Overhang Correction = Top Links or Bottom Links (default: none). Tutorial: Top Links "is especially critical when an assembly has overlapping subassembly links that, if connected, would result in errors in surface triangulation"; datum surface uses Bottom Links. — [About Resolving an Overhanging Corridor Surface](https://help.autodesk.com/cloudhelp/2015/ENG/Civil3D-UserGuide/files/GUID-49E7C910-1FB7-41C8-9FCD-BDF8A43A78FE.htm); [To Resolve an Overhanging Corridor Surface](https://help.autodesk.com/cloudhelp/2015/ENG/Civil3D-UserGuide/files/GUID-DDF4085B-E72B-4EEC-823A-76FD0BBDF95A.htm); [Tutorial Exercise 1: Creating Corridor Surfaces](https://help.autodesk.com/cloudhelp/2015/ENU/Civil3D-Tutorials/files/GUID-FA79D184-B3AC-4B97-B9E2-349C2909D03C.htm); [Arkance: Corridor Surface Overhang Corrections](https://ukcommunity.arkance.world/hc/en-us/articles/21547037854738-Civil-3D-2014-Corridor-Surface-Overhang-Corrections)
- Retaining-wall subassembly in corridors: "offset of wall vertical face is driven by wall height" (snippet). — [Civil 3D Subassembly Reference (retaining wall)](https://help.autodesk.com/cloudhelp/2015/ENU/Civil3D-Subassembly-Ref/files/GUID-993FB90F-1F9A-43BB-9987-C4157A6EDF63.htm)
- Heightmap engines: Unity Terrain "is heightmap based, which fundamentally cannot support overhangs (such as caves and arches)" and "doesn't even do cliffs very well" (community Q&A); Godot docs: a heightmap "cannot be used to model overhangs or caves, which would require multiple vertices at the same vertical location"; suggested fix: separate meshes. — [GameDev StackExchange timeline (Unity terrain caves)](https://backiee.wasmer.app/https_gamedev_stackexchange_com/posts/69577/timeline); [Godot HeightMapShape3D doc fix commit](https://remotebranch.eu/Stowage/godot/commit/fb9a5699a15a43ca60b70fea856fca0c989c788a); [jMonkeyEngine: terrain cliff](https://hub.jmonkeyengine.org/t/how-can-make-terrain-cliff/42794)
- Catlike Coding Hex Map 3: `enum HexEdgeType { Flat, Slope, Cliff }`; `|Δelevation| == 1` → Slope, larger → Cliff. In `TriangulateConnection`, a slope gets terraces, anything else is one quad: `AddQuad(v1, v2, v3, v4)` where v3/v4 are the same edge points placed at the neighbor's elevation, i.e. a cliff is "a vertical-looking step with no intermediate terraces". Corner triangles are dispatched on the three edge types (slope-cliff → `TriangulateCornerTerracesCliff`, both cliffs with slope on top → rotated calls, otherwise one plain triangle). - Hex Map 4: boundary point on a cliff must be computed from *perturbed* endpoints and itself not perturbed: "The solution is to not perturb the boundary vertex"; "To make the boundary point match the final cliff, we have to interpolate between the perturbed points." — [Catlike Coding: Hex Map 4, Irregularity](https://catlikecoding.com/unity/tutorials/hex-map/part-4/)
- Hex Map 10 (walls on a cliff): one side of the wall moves toward the near edge, the other toward the far edge; offset = far − near with Y zeroed to keep the top flat (snippet). — [Catlike Coding: Hex Map 10, Walls](https://catlikecoding.com/unity/tutorials/hex-map/part-10/)
- Student project (hex terrain): cliffs are "hex borders that are split apart vertically, with the gap filled in afterwards"; 3-way cliff corners caused problems with a midpoint method. (snippet) — [Univ. of Tartu CG project: HexTerrain](https://courses.cs.ut.ee/2020/cg-pro/spring/Main/Project-HexTerrain)
- Cities: Skylines 2: a retaining wall appears when a road is placed against a terrain ridge (translucent preview, then "a concrete wall"); at launch no standalone wall/quay assets; later quay walls were added and players report they "cut into the soil beneath them"; the Anarchy mod exposes Retaining Wall / Quay / Elevated / Tunnel assets. — [GameSkinny: CS2 retaining walls](https://www.gameskinny.com/tips/cities-skylines-2-how-to-build-retaining-walls/); [Paradox forum: quay wall functionality](https://forum.paradoxplaza.com/forum/threads/quay-wall-functionality-concerns-suggestions.1855280); [Anarchy mod page](https://sites.google.com/view/jaylyons/game-hub/cities-skylines-ii/mod-list-1/code-mods/anarchy)
- Transport Fever 2: retaining walls are mod assets (Enzojz "Open-cut Station & Retaining Wall"); tall walls make the terrain-deformation area spread too far; the author said this "could not be fixed within the game's terrain system". (snippets) — [Steam Workshop: Open-cut Station & Retaining Wall](https://steamcommunity.com/sharedfiles/filedetails/comments/2547220103); [Realistic Railway Slopes](https://steamcommunity.com/sharedfiles/filedetails/comments/2161175689)

### Inferences
- The CAD "double breakline with 1 mm offset" is a *data-model workaround*, not a rendering technique: it exists only because a TIN must be a function z(x,y). It produces a sliver triangle strip with a near-horizontal normal; CAD renders that fine because it shades smooth and never looks at it edge-on at 1 m scale. In a flat-shaded game mesh it is the wrong tool (see Q5).
- The game-engine pattern (Catlike Coding, Godot/Unity advice) is: keep the ground a strict 2.5D function per level, and insert *explicit* vertical quads between the lower and upper edge polylines; the bottom row of wall vertices is the lower terrain's edge vertices (same floats), the top row the upper terrain's (same floats). This is a genuine 3D mesh, so no height-function constraint applies.
- Civil 3D's "overhang correction" is the CAD analogue of "pick which side owns the wall foot": Top Links = the upper surface runs to the wall and drops, Bottom Links = the lower surface runs to the wall and rises. In a game mesh you make this explicit: the wall polyline is shared, upper level stops at the top edge, lower level stops at the bottom edge, and the wall quad strip joins them.

## Q2b. The civil-engineering corridor / daylight model (road + embankment stamped into terrain), precisely

### Takeaway
A Civil 3D corridor is sampled at stations along a baseline; at each station an assembly (cross-section of subassemblies) produces *points* (coded, e.g. Hinge_Cut, Daylight_Fill) joined by straight *links*; the daylight subassembly shoots a link from the hinge at the cut or fill slope until it hits the target (existing ground) surface. Points of the same code at successive stations are connected into *feature lines* along the corridor. The corridor surface is then a TIN using the points as data and the feature lines and links as breaklines, with daylight feature lines (left/right) forming the outer boundary so no triangulation leaks past the daylight line. This is exactly a piecewise-linear "road with embankment" with breaklines by construction.

### Cited Findings
- "A corridor surface uses corridor points as point data and uses feature lines and links like breaklines", "much as points and breaklines build a regular surface". (snippet, Autodesk doc) — [Civil 3D: Surfaces tab (Corridor Properties)](https://help.autodesk.com/cloudhelp/2015/ENU/Civil3D-UserGuide/files/GUID-3FD85EB7-4903-4832-BDFD-13F95EE19E5F.htm); [To Create Corridor Surfaces](https://help.autodesk.com/cloudhelp/2015/ENG/Civil3D-UserGuide/files/GUID-4B8A4B06-1442-48FB-AAC4-DBB0B6CCD99E.htm)
- Links and codes: "a link is defined as a single straight-line segment between endpoints"; point codes sit on link endpoints, link codes on segments; cut/fill daylight points "are a good example of where two codes may be needed for the same point"; "the limits-of-construction of the corridor model can be determined by extracting alignments or figures that connect the cut/fill daylight points on each side of the model". — [Civil 3D: About Point, Link, and Shape Codes for Subassemblies](https://help.autodesk.com/cloudhelp/2024/ENG/Civil3D-UserGuide/files/GUID-CBABE972-D690-49AE-A7DE-60F2E1B0675D.htm)
- Daylight subassembly: "inserts a link that daylights to a target surface at a user-defined cut or fill slope"; "The hinge point elevation is checked against the target surface to determine if the section is in the cut or fill condition"; "If no cut daylight point is found, the process is repeated for the fill condition"; where the slope crosses the surface more than once "an input parameter controls which intercept is used"; "If the daylight point is within the Min Width, the daylight point is moved to the minimum width point on the target surface"; codes Daylight_Cut / Daylight_Fill, Hinge_Cut / Hinge_Fill; target type: surfaces only. — [Civil 3D Subassembly Reference, daylight subassemblies](https://help.autodesk.com/cloudhelp/2025/ENU/Civil3D-Subassembly-Ref/files/GUID-BB29AEA5-F447-43C9-BA6D-01BD7E290A08.htm); [another daylight subassembly page](https://help.autodesk.com/cloudhelp/2025/ENU/Civil3D-Subassembly-Ref/files/GUID-EB213916-7C13-4AD9-8444-7D31E9656929.htm); [DaylightToOffset-type page](https://help.autodesk.com/cloudhelp/2024/ENG/Civil3D-Subassembly-Ref/files/GUID-D4CC86D2-C252-4841-A5BB-1A8ED06531FC.htm)
- Boundaries: "Use corridor surface boundaries to prevent triangulation outside of the daylight lines of a corridor surface"; types Render Only, Hide Boundary (holes, e.g. a median), Outside Boundary; "A single pair of daylight feature lines lets Civil 3D create the boundary automatically"; interactive: "first select the bottom end of one feature line, followed by the top end of its pair". — [Civil 3D Tutorial Exercise 2: Creating Corridor Surface Boundaries](https://help.autodesk.com/cloudhelp/2026/ENG/Civil3D-Tutorials/files/GUID-5F0C18E8-F32E-42C2-B381-551998705FF0.htm)
- Known artifact: where the daylight feature line has angled corners "TIN lines are wrong and the slope is not correct"; a user asked for an option to force TIN lines onto links (i.e. the cross-section links are not always honored as edges). — [Autodesk forum: corridor surface TIN lines always on links](https://forums.autodesk.com/t5/civil-3d-forum/improving-corridor-surface-tin-lines-always-on-links/m-p/7362351)
- Agency practice: daylight feature lines must be draped on the ground surface before building a surface from them; after adding corridor feature lines as breaklines, delete stray triangles. — [Wisconsin DOT C3D KB: rural intersection grading](https://c3dkb.dot.wi.gov/Content/c3d/rdwy-dsn/rurl-int/rurl-int-grdg-bhnd-cg-fl.htm); [WisDOT: best practices for breakline development](https://c3dkb.dot.wi.gov/Content/c3d/rdwy-dsn/rdwy-dsn-bst-prctc-brkln-dev.htm)
- Overhang correction (Top/Bottom Links) is needed because assemblies with curbs/walls are not a function of offset. — see Q2 sources ([About Resolving an Overhanging Corridor Surface](https://help.autodesk.com/cloudhelp/2015/ENG/Civil3D-UserGuide/files/GUID-49E7C910-1FB7-41C8-9FCD-BDF8A43A78FE.htm))

### Inferences (algorithm, reconstructed from the documented pieces)
1. Sample the road axis at stations s_i (Civil 3D: a frequency, plus extra stations at geometry changes).
2. At each station build the cross-section left and right: pavement edge, curb, verge → *hinge* point H at offset w, height z_road(s_i) + profile.
3. Daylight: from H, march outward along a line of slope −1/k (fill) or +1/k (cut) until it intersects the existing-ground profile g(s_i, t) (piecewise-linear across the terrain triangles); choose cut vs fill by comparing z_H to g at the hinge; pick the first (or n-th) intercept; enforce a minimum width. Result: daylight point D_i (left and right).
4. Connect same-coded points across stations into feature lines: road edge polyline, hinge polyline, daylight polyline (left/right).
5. Build the TIN: vertices = all station points; breaklines = all feature lines (longitudinal) and all links (transverse cross-section segments); outer boundary = daylight-left + end sections + daylight-right. Nothing is triangulated outside.
6. Merge with existing ground: cut the ground TIN along the daylight boundary (the daylight polyline is a breakline in the ground too) and paste the corridor surface inside it. In Raatstad terms: the daylight polyline is the "voet van het talud" and your `LineGround` already does exactly this per cell; the corridor view says *also* the hinge line and road edge must be edges, and the cross-section links (perpendicular cuts at stations) are optional edges the TIN may or may not follow — which is the source of the forum complaint about slopes being wrong at corners.
7. Where the slope would be vertical (retaining wall): CAD inserts a wall breakline (double line) or applies overhang correction; a game should instead stop the ground at the wall foot/top polylines and add a wall quad strip (Q5).

## Q3. Exact agreement on shared edges between independently generated patches

### Takeaway
Cracks between patches have two distinct causes: topological T-junctions (a vertex on one side has no counterpart on the other) and numerical mismatch (the "same" vertex computed by two code paths differs in the last bits). The documented remedies are: never let a vertex lie on a neighbour's edge without the neighbour also having it (split the edge), compute every shared-edge vertex from identical inputs in one global coordinate space (ideally one function that both patches call with the edge's canonical endpoints), make shared vertices bit-identical (shared indices or exact duplicates), and, as a last resort, hide residual gaps with skirts. Clipper2-style integer/fixed-point coordinates make "equal" well-defined.

### Cited Findings
- T-junction definition: "a vertex lying on a shared edge that connects to a polygon defined in only one of the two primitives". — [US patent 6,940,505 (dynamic tessellation)](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/6940505)
- "anywhere you have a T-junction one side will have a straight edge while the other side has two edges"; stitching "modifies the index buffer so patch edges match their neighbours"; alternative: fixed pattern of degenerate triangles/stitch strips; skirts: "duplicates border vertices and drops them downward", "isn't technically rigorous", "could fail if looking at the terrain from a top down view with a zig-zag mismatch"; overlap between tiles (No Man's Sky cited) leaves "very rare artifacts". (snippets; page 403) — [GameDev.net: terrain LOD and cracks](https://gamedev.net/forums/topic/713470-terrain-lod-and-cracks); [GameDev.net: terrain patch stitching preferences](https://gamedev.net/forums/topic/493389-terrain-patch-stitching-preferences/4220825/)
- Khronos thread (fetched): "Such cracks can occur with very small differences in floating point values"; double precision on the CPU did not help ("graphics cards don't support doubles internally"); when adjacent triangles "use EXACTLY THE SAME vertices on an edge" pixel errors are avoided, recommendation "to share the vertices and render your triangles indexed"; uploading identical duplicates "usually works"; computing the same position two ways on the GPU can z-fight, so bit-identical results across code paths are not guaranteed; adjusting T-junction vertex heights to lie on the long edge still left single-pixel holes; the proper fix is tessellating the larger edge; MSAA "largely gets rid of the problem" as a palliative; "games have shipped with T-junction problems" (Quake 3). — [Khronos: Single pixel cracking issue](https://community.khronos.org/t/single-pixel-cracking-issue/55383)
- Other threads: "if a vertex lies on an edge, that edge should be split into two collinear edges"; insert the intersection vertices. (snippets) — [Khronos: OpenGL renderings lack of precision](https://community.khronos.org/t/opengl-renderings-lack-of-precision/39774); [Khronos: polygon tears](https://community.khronos.org/t/polygon-seems-tears-please-help/44495)
- Chunked LOD (Ulrich, SIGGRAPH 2002): "Each chunk has a skirt, which is a strip of triangles around the edge of the chunk extending down below the surface. The skirts are part of the precomputed triangle meshes"; neighbors at different resolutions produce "T-junctions that can cause visible cracks"; skirts avoid sewing chunks together ("we just place chunks beside each other, and use skirts to fill the gaps"). — [UChicago CS 23700 project 4 (chunked LOD)](https://classes.cs.uchicago.edu/archive/2014/winter/23700-1/project_4_and_5/project-04.pdf); [yaldex game-programming chapter on Ulrich's chunked LOD](https://www.yaldex.com/game-programming/0131020099_ch14lev1sec5.html); [TU Wien thesis: Geospatial Rendering in Unity 3D](https://www.cg.tuwien.ac.at/research/publications/2014/ZAU14/ZAU14-thesis.pdf); [Khronos: Chunked LoD cracks](https://community.khronos.org/t/chunked-lod-cracks/72110)
- Procedural chunk seams: "Chunk seams misalign when neighboring chunks compute edge vertices with subtly different inputs"; "Feed the noise function global world coordinates, not per-chunk local coordinates. When each chunk uses its own origin, the shared edge evaluates to two different heights"; "test that two adjacent chunks computing a shared edge agree to the bit"; avoid seeding from floating-point coordinates "that round differently on different hardware", use integer coordinates + world seed; weld boundary vertices or overlap as fallback. — [bugnet.io: procedural mesh seams from mismatched noise sampling](https://bugnet.io/blog/how-to-fix-procedural-mesh-seams-from-mismatched-noise-sampling); [bugnet.io: procedural generation seams and gaps](https://bugnet.io/blog/how-to-fix-procedural-generation-seams-and-gaps); [bugnet.io: bug reporting for procedural terrain](https://bugnet.io/blog/bug-reporting-for-games-with-procedural-terrain)
- Catlike Coding: edge vertices for a neighbor are derived from the *same shared corners* ("we also need to compute extra edge vertices for the neighboring cell"); `EdgeVertices` holds the points "ordered clockwise along a cell's edge" and its constructor "takes care of computing the intermediary edge points"; perturbation samples a noise texture by world position with bilinear filtering so a given world position always gets the same offset; cracks appeared "because we're not consistently using the same cell heights when triangulating the mesh"; per-vertex Y is not perturbed (per-cell instead). — [Catlike Coding: Hex Map 4, Irregularity](https://catlikecoding.com/unity/tutorials/hex-map/part-4/)
- Quadtree terrain guidance: limit LOD difference between neighbors and share boundary vertex indices; stitching only as fallback. (snippet) — [Volcengine Q&A on terrain T-junctions](https://www.volcengine.com/article/751776)
- Mesh repair tools close T-junctions by merging near-duplicate vertices (a "70% of cases" figure is quoted there but unverified). — [3D geospatial: fixing non-manifold edges](https://3d-geospatial-com.pages.dev/3d-geospatial-fundamentals-for-digital-twins/mesh-topology-basics/fixing-non-manifold-edges-in-3d-meshes/)
- Clipper2 uses integers so that "integer imprecision is constant" (±1 unit) and significant error is distinguishable from insignificant error; floats are "much less precise" at large magnitudes. — [Clipper2: Robustness](https://www.angusj.com/clipper2/Docs/Robustness.htm)

### Inferences (recipe)
- Edge ownership: give every undirected cell edge a canonical key (min(cellA,cellB), max(...)) and a canonical direction (from the lower-indexed cell's corner order). One function `EdgePolyline(key)` computes the full ordered vertex list on that edge (both corners, every breakline crossing, every wall foot/top). Both cells call it and *reverse* it when their winding requires; they never recompute a crossing from their own plane data. This is the direct generalization of Catlike Coding's `EdgeVertices`-from-shared-corners.
- Deterministic evaluation: compute shared-edge crossings in one global frame (planet frame, double precision), from the *same* pair of planes in the *same* order (sort the two planes by a stable id before intersecting), and only then cast to float for the mesh. Different operand order (a+b vs b+a is fine, but (a+b)+c vs a+(b+c) is not) is enough to break bit equality.
- T-junction rule: a cell may insert interior vertices freely, but any vertex on a boundary edge must come from `EdgePolyline`; the cell's own clipping must therefore clip against the edge's crossing points too (i.e. a crease line that ends exactly on the edge produces a vertex that the neighbour also receives, even if the crease does not continue into the neighbour). If the neighbour's surface is a different function, it still must carry that vertex (collinear split, zero geometric effect).
- Snapping: quantize all shared-edge vertices to a lattice (e.g. 1 mm or 2^-10 m) *after* exact computation and *before* use in either cell; equality then is integer equality. Merging vertices closer than the lattice step eliminates slivers at the source (Q4).
- Skirts/overlap are for LOD mismatch, not for this problem: here both sides can be made identical, so stitching by construction is the right answer; skirts would also show from top-down views (documented failure mode above).
- Chunk vs cell: the same ownership rule applies at chunk boundaries (`ChunkN` = 128 cells); a chunk mesh is just the union of cell meshes, so if cells agree, chunks agree. Keep the shared-edge polylines cached by key (`groundCache`-style) so both chunks read the same object.

### Gaps
- No authoritative source on C#/.NET floating-point determinism across code paths (JIT, FMA contraction) was found; the above "same function, same operand order" rule is an inference. Unity's Burst/IL2CPP may reorder; verify by a bit-equality test as the bugnet post recommends.

## Q4. Robust polygon splitting by lines (half-plane clipping, epsilons, slivers, snap rounding)

### Takeaway
Sutherland–Hodgman against one half-plane at a time is the standard way to cut a convex polygon by a line; its known failure modes are duplicate/degenerate output vertices and (for concave input) coincident edges, fixed by dropping consecutive duplicates and discarding pieces with <3 vertices or near-zero area. For robustness, the geometry literature converges on integer/fixed-point coordinates (Clipper2: ±1 unit error, near-zero-area polygons removed) or exact predicates (Shewchuk) with snap rounding to return to floats (Devillers–Lazard–Lenhart 3D snap rounding; Mesh Arrangements uses exact arithmetic and "no general position assumptions").

### Cited Findings
- Sutherland–Hodgman: clips the subject polygon against each convex clip edge in turn, treating the edge as an infinite line and keeping vertices on the inside; four in/out cases per polygon edge; with concave subjects the output can contain "coincident or overlapping edges", acceptable for rendering but not for e.g. shadows; a single output list joins last to first and can produce extraneous lines. — [DCA/UFRN lecture: Sutherland–Hodgman](https://dca.ufrn.br/~lmarcos/courses/compgraf/notes/viewing/tsld033.htm); [Vikram Univ. notes on polygon clipping](https://vikramuniv.ac.in/files/wp-content/uploads/M.Sc_.-IV_ComputerGraphics_PolygonClipping_Bhupendra_K_Pandya.pdf)
- Weston (Wayland compositor) replaced its clipper because "the existing algorithm had some corner cases ... degenerate polygons appearing under rotation"; the replacement emits vertices in clockwise order and discards duplicate vertices and degenerate polygons. — [Weston commit: cliptest.c](https://code.tokarch.uk/mainnika/weston/commits/commit/00db2ee5ffd3934f2699e17f5ba793c86d87b27d/clients/cliptest.c)
- Clipper2: "Clipper uses integers internally for all geometric calculations"; integer rounding error is ±1 unit; "solutions shouldn't be expected to contain polygons with near-zero area"; a triangle with an edge under 2 units is treated as zero-area and removed; scale coordinates so rounding is insignificant; discretization can still create tiny self-intersections, scaling ×100 reveals them; accepted integer range ±0x3FFFFFFFFFFFFFFF (~±4.6e18); doubles are converted to integers before clipping. — [Clipper2: Robustness](https://www.angusj.com/clipper2/Docs/Robustness.htm); [Clipper2: Overview](https://angusj.com/clipper2/Docs/Overview.htm); [Clipper2 FAQ: floating point coordinates](https://angusj.com/clipper2/Docs/FAQ.htm); [Clipper1: Rounding](https://angusj.com/delphi/clipper/documentation/Docs/Overview/Rounding.htm)
- Exact approach: Zhou, Grinspun, Zorin, Jacobson, "Mesh Arrangements for Solid Geometry" (SIGGRAPH 2016, ACM TOG 35(4)): "The two-stage method makes no general position assumptions and does not resort to numerical perturbation"; cells of the arrangement get a winding-number vector; implemented in libigl, gptoolbox, PyMesh and Blender; code uses CGAL. Follow-ups describe it as rational-arithmetic, topologically guaranteed, slow (one reports 56× faster). — [Columbia project page](http://www.cs.columbia.edu/cg/mesh-arrangements/); [paper PDF](https://www.cs.columbia.edu/cg/mesh-arrangements/mesh-arrangements-siggraph.pdf); [Jacobson blog](https://alecjacobson.com/weblog/4573.html); [Replicability review](https://graphicsreplicability.github.io/replicability.graphics/papers/10.1145-2897824.2925901/index.html); [2024 mesh-arrangements follow-up](https://mangoleaves.github.io/files/2024-mesh-arrangements/MeshArrangements.pdf)
- Snap rounding: Devillers, Lazard, Lenhart (2020) give "the first algorithm for rounding a set of interior-disjoint polygons into a simplicial complex whose vertices have integer coordinates"; iterated snap rounding (2D) keeps each vertex at least half a pixel from any non-incident edge. Exact methods must round back to floats eventually ("exponential growth in the size of the coordinate representation" otherwise); Cherchi et al. delay coordinates to the end and use an iterated cast-to-float heuristic, which "may invalidate the embedding"; Lévy 2024 lists snap-rounding integration as future work. — [Devillers–Lazard–Lenhart, 3D snap rounding (DCG 2020)](https://springerlink.bibliotecabuap.elogim.com/content/pdf/10.1007/s00454-020-00202-2.pdf); [Convex polyhedral meshing for robust solid modeling (arXiv 2109.14434)](https://arxiv.org/pdf/2109.14434); [Lévy, Exact predicates, exact constructions and combinatorics for mesh CSG (arXiv 2405.12949)](https://arxiv.org/pdf/2405.12949); [trueform: Fast and robust mesh CSG (arXiv 2607.15905)](https://arxiv.org/pdf/2607.15905); [Halperin, snap rounding seminar notes](https://www.uni-trier.de/fileadmin/fb4/prof/INF/DEA/Seminar0708/Halperin.pdf)
- Shewchuk's `orient2d` gives the exact sign of the side-of-line test for double inputs (see Q1). — [Robust predicates abstract](https://people.eecs.berkeley.edu/~jrs/papers/robust-predicates.abstract)

### Inferences (concrete procedure for "split a convex face polygon by every plane–plane crease line")
1. Work in a local 2D frame per cell (tangent plane of the cell on the sphere) in double precision; represent each plane as (a,b,c) with z = a·x + b·y + c.
2. For the min/max-of-planes surface restricted to the cell polygon P: for each pair of active planes (i<j, sorted by stable id) compute the crease line L_ij: (a_i−a_j)x + (b_i−b_j)y + (c_i−c_j) = 0. Skip if the normal is below a threshold (parallel planes → no crease).
3. Snap: quantize line coefficients? No; instead quantize *points*. Clip P by the half-planes of L_ij successively (Sutherland–Hodgman); each clip yields two convex polygons. Compute each intersection vertex as segment–line intersection in doubles, then snap it to the lattice (e.g. round(x·1000)/1000 for mm). For boundary edges, do *not* compute the crossing locally: take it from the canonical `EdgePolyline` (Q3) by matching the lattice point.
4. After each clip: drop consecutive duplicates (lattice equality), drop polygons with <3 vertices or |area| < ε_area (Clipper2's "edge under 2 units" rule is a good template: drop any triangle whose shortest edge is < 2 lattice units).
5. Only keep the sub-polygon pieces where the pair (i,j) is actually the active pair (evaluate min/max at the centroid of each piece; assign the piece to its winning plane). Pieces with the same winning plane that share an edge can be merged back (optional, keeps triangle count low).
6. Triangulate each convex piece by fan from the vertex with the largest angle sum / or shortest diagonals; no CDT needed since pieces are convex and planar.
7. Classify crease edges as "hard" (slope change) vs "wall" (height jump): a crease between two *height levels* that are not continuous across it (your `Cut`/`Quay`/`Keermuur`) is not a crease of one function but a boundary between two functions; handle via Q5 (two edge polylines, same XY, different Z, plus wall quads).
8. Sub-grid sampling alternative: sampling a fixed sub-grid and letting the crease be approximated is what heightmap engines do; it produces a staircase/zig-zag crease, which in low-poly flat shading is visible as alternating triangle normals along the line. Exact splitting (above) is what both the TIN-with-breaklines (CAD) and the corridor model do, and what the user's `LineGround` already does; stay with exact splitting.

### Gaps
- No single paper found that treats "piecewise-planar min/max surface meshing" as such; the above is assembled from CAD breakline practice + clipping robustness literature.

## Q5. Flat-shaded low-poly rendering: per-face normals, vertical wall quads, winding, the wall–ground seam; is a 2 cm sliver acceptable?

### Takeaway
Nothing in the sources supports using a thin near-vertical sliver as a stand-in for a wall; flat-shading literature says slivers "stand out" because shading is per triangle, and CAD's 1 mm wall offset exists only because the TIN format cannot hold a vertical face. Best practice from mesh-based hex terrains is a dedicated quad strip between the lower edge polyline and the upper edge polyline, with its own (horizontal) face normal, bottom vertices equal (bit-identical) to the lower terrain's edge vertices, top vertices equal to the upper terrain's edge vertices, and separate vertex records so the flat normals do not blend.

### Cited Findings
- Flat shading and slivers: a Godot Voxel user who switched to flat shading (normals from screen-space derivatives) found the marching-cubes mesher's slivers stand out because "shading is based on triangles and not on normals computed by the mesher"; the maintainer's remedy is to clamp interpolation factors so triangles do not become too thin. — [godot_voxel issue #714](https://github.imc.re/Zylann/godot_voxel/issues/714)
- Polycount on slivers: "triangles with very small angles in one or more vertices"; they cause baking/UV problems and "artefacts with lighting (caused by problems with normals)". — [Polycount thread (slivers)](https://polycount.com/discussion/comment/2674648); [Polycount (lighting artefacts)](https://polycount.com/discussion/comment/2674671)
- Z-fighting is a coplanar/near-coplanar surface problem in a per-pixel depth buffer; the fixes are depth bias or offsetting geometry. — [Polycount (z-fighting is per-pixel)](https://polycount.com/discussion/comment/2213096); [Configura: Z-fighting](https://support.configura.com/hc/en-us/articles/360039738634)
- Catlike Coding cliff: an edge connection with a cliff is one `AddQuad(v1, v2, v3, v4)` from the lower cell's edge points to the same points at the neighbour's elevation; corner cases are fanned to a boundary point *on the cliff*; keeping terraces level across a cliff would need quads whose sides don't share a slope, "The result will look messy." — [Catlike Coding: Hex Map 3](https://catlikecoding.com/unity/tutorials/hex-map/part-3/)
- Catlike Coding: the boundary vertex on a cliff is computed from already-perturbed endpoints and is itself not perturbed, so the cliff quad and the corner fan meet exactly. — [Catlike Coding: Hex Map 4](https://catlikecoding.com/unity/tutorials/hex-map/part-4/)
- Chunked-LOD skirts are vertical strips "extending down below the surface" that are *hidden* fill geometry; course notes warn they "can shadow bake oddly along steep cliffs" and fail in top-down views with zig-zag mismatch — i.e. vertical hidden strips have visible side effects in lighting. — [UChicago project 4](https://classes.cs.uchicago.edu/archive/2014/winter/23700-1/project_4_and_5/project-04.pdf); [GameDev.net: terrain LOD and cracks (snippet)](https://gamedev.net/forums/topic/713470-terrain-lod-and-cracks); [pulsegeek: terrain stitching and chunking](https://pulsegeek.com/articles/terrain-stitching-and-chunking-seamless-streaming/)
- Civil 3D: a wall is a double breakline with an imperceptible offset *because* a TIN cannot be vertical (Q2 sources); community reports of "grades everything weird" and "broken surface" with that method. — [Arkance: Retaining Wall using Grading](https://emea.support.arkance.world/hc/lt/articles/36468675238034-How-to-create-Retaining-Wall-using-Grading); [AUGI thread](https://forums.augi.com/archive/index.php/t-79230.html)
- Shared, bit-identical vertices on an edge avoid pixel cracks; T-junction heights adjusted onto the long edge still leave single-pixel holes. — [Khronos: Single pixel cracking issue](https://community.khronos.org/t/single-pixel-cracking-issue/55383)

### Inferences (practitioner rules)
- Is a 2 cm sliver acceptable as a wall? No. (a) Its face normal is nearly horizontal but its projected area is ~2 cm, so in flat shading it renders as a 1–2 pixel bright or dark line that flickers with view angle (the godot_voxel "slivers stand out" effect). (b) Seen from above, the upper and lower terrain triangles adjacent to it are nearly coplanar in screen space with the sliver → the "teeth" look along the crest. (c) At 1 m = 1 unit, 2 cm is 100× the ±1 mm lattice but still below the float precision envelope at planet radius 600 m (float ulp at 600 is ~6e-5 m, fine), yet any clipping epsilon ≥ 2 cm (sliver removal, Clipper2's "edge < 2 units" rule) would delete it, so it is fragile by construction. (d) It makes the terrain mesh a non-function locally without being an honest wall: collision/walking (`PlanetWalker`) and `SurfaceH` lookups get a 2 cm ramp.
- Correct construction (from Catlike's cliff quad generalized to arbitrary wall polylines):
  1. The wall is a polyline W = [w_0 … w_n] in XY (on the sphere: along the cell tangent plane), owned canonically like an edge (Q3). Two height functions apply: z_low(w_k) and z_high(w_k), both evaluated by one shared function and snapped.
  2. The lower terrain is clipped so that W is one of its boundary polylines (vertices exactly w_k at z_low). The upper terrain is clipped so that W is one of its boundary polylines (vertices exactly w_k at z_high). Both contain *all* w_k (no T-junctions along the wall).
  3. For each segment (w_k, w_{k+1}) emit one quad (two triangles) with vertices (w_k,z_low),(w_{k+1},z_low),(w_{k+1},z_high),(w_k,z_high), wound so the face normal points toward the low side (the only side from which the wall is visible if the high side is solid ground). Where the wall is visible from both sides (a free-standing quay with water), render two-sided by emitting both windings rather than a two-sided shader, so each side keeps its own flat normal.
  4. Flat shading: give the wall quad its own vertex records (do not share vertex *indices* with the ground even though positions are identical), so the per-face normal is not averaged with the ground normals. Positions must still be bit-identical floats: copy them from the same snapped `EdgePolyline`/wall polyline array, never recompute.
  5. Where z_high − z_low drops to 0 (wall fades out into a talud), end the wall at the first k where the gap is below the lattice step and merge w_k into the ground crease; emit a triangle instead of a quad for the last segment if only one end has zero height.
  6. Corners where a wall meets another wall or a cliff edge: follow Catlike's rule — compute the shared corner once, do not perturb or re-derive it, fan triangles to it.
  7. Keep the wall in a separate submesh/material (concrete/brick) so it can get a different texture and so its normal is never touched by any smoothing pass on the terrain.
- Avoid z-fighting at the wall foot: do not let the lower ground overlap the wall footprint (clip exactly to W); a strip of ground running *under* the wall by a few cm is a coplanar-ish overlap seen edge-on and will shimmer.

### Gaps
- No source quantifies "how thin is too thin" for flat shading at a given pixel scale; the 2 cm judgement is reasoning, not a measured result.
- No Unity-specific document on two-sided flat shading was retrieved; the "emit both windings" advice is standard practice but uncited here.
